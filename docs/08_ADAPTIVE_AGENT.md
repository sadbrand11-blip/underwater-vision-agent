# 0.3.0：根据观察选择动作和重新规划

## 怎么使用

1. 双击项目中的 `双击启动.bat`，打开对话工作台。
2. 上传水下图像，或点击“使用 D 盘示例图”。
3. 调度策略保持“动态目标与规划”。要使用 DeepSeek，再将运行方式改为“真实大模型对话”；离线模式是明确标注的规则示例。
4. 输入：“检查这张水下图，必要时校正曝光，然后只识别管道，说明结果是否可靠。”
5. 查看目标类别、初始计划、候选比较、计划修订和执行过程。计划只是拟议动作，工具记录才说明实际做了什么。

旧调度可在同一页面选择“原有受限调度（对照）”。它与实验报告中的固定 Workflow 不是同一基线。原有完整分析页面和双击启动入口继续可用。

## 优化思路

之前，模型主要选择预设任务和工具组合。现在，它先明确完整目标、提出计划，再读真实观察，选择校正方法、比较候选并调整计划。程序只限定能力、前提、完成条件与可靠性规则；执行顺序和候选方法由模型决定。

**用户任务 → 固定目标 → 简短计划 → Action → 工具执行 → Observation → 继续或修订计划 → 程序检查完成 → 结果。**

| 部分 | 负责什么 | 你在网页上能看到什么 |
|---|---|---|
| 目标契约 | 固定任务、目标类别、图片、校正策略和可靠性要求 | “管道”展开为 `pipe` 与 `pipe_type2`；未知类别不偷偷删除 |
| 初始计划 | 模型说明拟执行动作和目的 | 计划单独展示，不计作工具已经执行 |
| 工具与观察 | 本地计算质量、生成候选、检测、比较、检索 | 真正的调用、参数、缓存、耗时和观察编号 |
| 重新规划 | 根据实际观察改变动作，最多两次 | 改变原因、引用的观察编号和新计划 |
| 完成校验 | 防止缺证据、错图片或改写可靠性 | 完成、未完成、澄清或不支持，与视觉可靠性分开显示 |

这属于受约束的工具型 Agent。任务范围、校正算法和可靠性检查仍由工程规则限定。加入规划记录不能证明通用自主能力；真实模型是否依据观察调整行动，要看独立评测和实际轨迹。

## 三种路径

| 图像状态 | 程序允许的行为 | 结果边界 |
|---|---|---|
| 正常 | 原图检测，加单帧内部可靠性检查 | 未取得跨曝光一致性证据，不把自比较当作多曝光验证 |
| 偏暗、仍可评估 | 模型选 Gamma 或局部候选；评估、检测和比较后采用候选或原图 | 框数或分数上升不等于准确率提高 |
| 严重丢失信息 | 停止校正，输出质量失败及原因 | 全黑、完全饱和等区域的真实纹理不能从单帧确定 |

候选检测退化时，模型须引用真实比较观察记录重新规划，再决定保留原图或尝试另一方法。所有已尝试的候选都要有比较证据，不能隐去不利结果。

## 两种候选为什么有界

| 方法 | 做什么 | 限制 |
|---|---|---|
| `gamma_only` | 沿用原亮度中位数计算 Gamma，范围 0.65–1.45 | 只改变亮度映射，不生成纹理 |
| `local_bounded` | 沿用 Gamma、有限 CLAHE 混合和条件降噪 | 与原视觉流程相同参数，不为获得高分而临时调阈值 |

每张原图每种方法只生成一次；重复请求复用缓存。两种候选均直接从原图产生，候选不能再增强。正常曝光返回未调整状态；不具备质量前提时不生成候选。原图和候选像素受保护，配置或检测器变化时旧缓存不能用于完成任务。

## 图片与目标的一致性

- “校正后的图”指最近生成的候选；“刚才采用的图”指任务开始时的最终选择。生成两种候选时，它们可能不是同一张。
- 所有六类原始检测保存在本会话缓存里。用户请求的类别由程序过滤；数量、报告和框图使用相同结果。
- 单纯检测只交付候选框，不能声称完整可靠性。没有候选可以正确完成检测，但不能证明画面没有目标。
- 原有会话锁、闲置30分钟过期和上限继续生效；动态模式另存状态和报告，避免混用旧调度证据。

## 限制与错误恢复

目标解析、初始规划、后续调度全部共用每轮10次模型调用、12次工具调用、180秒限制。格式纠错最多两次；连续两次工具错误停止，展示已完成结果。修订计划也是一次工具调用。工具顺序允许等价安排；同批调用按顺序执行，未满足前提会返回结构化错误。

LLM只能选择存在的图片、观察和引用。最终测量、框、类别计数和可靠性由程序生成。日志先脱敏再保存；像素保存在本地，云端仅接收任务文字、指标、框结果和检索片段。

## 接口与复现实验

`/api/chat` 新增 `agent_mode: adaptive|legacy`，未提供时维持旧行为。动态返回增加 `goal_contract`、`initial_plan`、`plan_revisions`、`selected_image_id` 和 `computation_counts`。

```powershell
# 零HTTP请求检查输入、题目和图片前提
python evaluate_adaptive.py --backend live --preflight --run-id my-adaptive-run --phase before
# 小批开发；随后再运行相同编号的真实视觉演示
python evaluate_adaptive.py --backend live --run-id my-adaptive-run --phase before --split dev
python evaluate_adaptive.py --backend live --run-id my-adaptive-run --phase before --split demo --resume
```

这些命令会使用你本地的 API。每个运行编号独立保存不可重置的120次HTTP上限，重试也计入。中断记录保留失败，继续运行不覆盖已有成功或失败；配置、代码、题目、权重、知识或图片哈希变化会阻止恢复。仅有一个 `fix1` 开发修复阶段，复测另存，同编号仍共用原计数器。

本轮题目在 `eval/adaptive_tasks.json`，预期标签由开发助手预先编写，未经外部人工复核。评分字段不随请求发送；开发修复提示包含一道追问题的具体解析示例，4/4属于见过开发题的回归，不是独立泛化。6个开发案例使用固定视觉夹具测试调度；3个演示输入使用现有SODD检测器，各运行两次。后两种输入是模拟变暗与全黑，数据及图片缓存留在D盘，不下载新数据。

固定 Workflow 使用同一工具和类别过滤：可校正时固定尝试两种方法，然后比较；没有LLM或规划修订成本。其限定中文解析是规则实现，不能据此比较一般中文理解能力。处理顺序为动态在先、固定在后，耗时还可能受模型预热影响。
